# 头像管理 — 需求规格（定稿）

> 对齐时间：2026-09-11　状态：待评审后开工
> 前置研究结论见文末「附录 A：图源实测记录」

## 1. 目标

fmps-web 新增**头像图片管理**能力：三类头像的缺失检测、自动获取、人工补充、发布上传。
替换现在纯手工的流程（手工去站点下载 → 手工转格式 → 手工上传 COS）。

## 2. 三类头像与真实图源（已实测确认）

| 本地目录 | 尺寸 | COS key | 图源 | 自动化 |
|---|---|---|---|---|
| `stu_icon_db_png/{Id_db}.png` | 200×226 | `stu_icon_db_png/{Id_db}.png` | `schaledb.com/images/student/collection/{Id_db}.webp`（同尺寸，转码即可） | 100% |
| `stu_icon_db/{Id_db}.jpg` | 200×226 | `stu_icon_db/{Id_db}.jpg` | 同上（PNG 转 JPG 得到） | 100% |
| `gacha-img/{Id_db}.png` | 200×200 | `gacha-img/{Id_db}.png` | `bluearchive.wikiru.jp` 的 `?★3`/`?★2`/`?★1` 页面上的 `<日文名>_icon.png` | 100%（名字映射后） |

- 本地目录命名**与 COS key 完全一致**，避免映射歧义。落在 `server/data/img/` 下。
- **必须用 `Id_db` 取图**：`sms_studata_main.json` 的 `Id` 字段是 generator.js 合成的顺序号（`String(10000+i)`），不是 schaledb 真实 Id。
- **必须用 `Name_jp` 去映射 wikiru 文件名**。

### 2.1 wikiru 抓取细节

- 页面：`?★3`(211 张) + `?★2`(24) + `?★1`(38) = **273 张**，覆盖库内 270 个学生。
- 图片路径规律：`attach2/696D67_<文件名的 UTF-8 十六进制>.png`
  （`696D67_` 是 ASCII `img_` 的 hex；解码后得到 `<日文名>_icon.png`）
- ⚠️ HTML 写的是 `width="60" height="60"`（**显示尺寸**），文件真实尺寸是 **200×200**。
- 由于各页面的攻击面不同，解析失败要给出明确报错，不能静默返回空。

### 2.2 命名变体归一化规则（缺一不可）

| wikiru 文件 | 库内 `Name_jp` | 规则 |
|---|---|---|
| `エイミ（臨戦）_icon.png` | `エイミ(臨戦)` | 全角（）→ 半角() |
| `アズサ_水着_icon.png` | `アズサ(水着)` | `X_形态_icon` → `X(形态)` |
| `オトギ_icon2.png` | `オトギ` | `_icon2` = 同名角色的第二个变体（**合法目标**） |
| `ホシノ（臨戦）スタイル1_icon.png` | `ホシノ(臨戦)` | 剥离 `スタイルN` |
| `アコ_仮icon.png` | — | 占位图（アコ/カエデ/トモエ/マリナ/ミモリ 共 5 个），默认排除 |

## 3. 已确认的决策

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 管理范围 | **三类全管**（stu_icon_db_png + stu_icon_db + gacha-img） |
| 2 | gacha 图获取方式 | **从 wikiru 抓成品图直接改名**（不裁剪）。支持手动上传作为兜底 |
| 3 | 抓取触发策略 | **新增优先 + 全量校验**：日常只补缺图；另给「全量校验」按钮做 273 张逐张比对 |
| 4 | 历史存量 | **拉 COS 现存当基线**（gacha 269 张 / stu_icon_db_png 268 张 / stu_icon_db(jpg) 91 张） |
| 5 | 异常处理 | **列候选让人点选**（同名变体 + 全部 273 张缩略图） |
| 6 | 发布联动 | **随发布一起上传 COS**，且必须在最终确认页呈现 |
| 7 | 发布确认页 | 要 4 项全有：每文件可折叠明细、数量统计总览、图片清单与体积、历次发布记录对比 |

## 4. 功能清单（分阶段）

### P0 — 能跑通主链路
1. **存储层**：`server/data/img/{stu_icon_db_png,stu_icon_db,gacha-img}/` 目录 + 读写封装。
2. **COS 基线同步**：HEAD 探测 + 下载缺失文件；冲突时以本地为准，不覆盖。
3. **schaledb 生成**：拉 `collection/{Id_db}.webp` → 转 200×226 PNG + JPG，写入两个目录。
4. **wikiru 抓取**：三页面 → 解析 → 归一化 → `Name_jp` → `Id_db` → 落 `gacha-img/`。
   - 返回三类结果：**新增 N 张 / 已存在跳过 M 张 / 异常 K 张（含原因）**
   - 支持可配置代理（默认直连）
5. **头像管理页**（`/icons`）：
   - 三个 tab（按类型切）+ 统计条（本地 x / COS y / 缺失 z）
   - 表格列：缩略图 | Id_db（加粗凸显）| 中文名 | 日文名 | 三类图状态（✅/❌/⚠️）| 来源 | 操作
   - 筛选：只看缺图 / 只看异常 / 按 Id_db 段
   - 工具栏：同步 COS 基线、从 schaledb 生成、抓取 wikiru（新增优先）、全量校验
   - 学生列表页加「缺头像」筛选项 + 入口按钮

### P1 — 人工补充与校验
6. **全量校验**：本地 / COS / wikiru 三方逐张比对，输出「仅本地有 / 仅 COS 有 / 三方不一致」清单。
7. **异常候选选择**：异常条目点开抽屉，网格展示候选图（同名变体优先，其次全量 273 张），点选确认落库。
8. **手动上传/替换/删除**：单张拖拽上传、覆盖替换、删除；支持按学生批量。
9. **学生详情页接入**：三类头像预览 + 单独的「重新生成 / 上传 / 替换」按钮。

### P2 — 发布链路
10. **图片随发布上传 COS**：向 `stu_icon_db_png/`、`stu_icon_db/`、`gacha-img/` 三个前缀推图。
11. **发布最终确认页增强**（4 项）：
    - 每个 JSON 文件**可折叠**，展开为字段级红绿 diff
    - 顶部**数量统计总览**：新增/删除/修改的文件数、条目数、字段数
    - **图片清单与体积**：新增/变更图片列表 + 单张与总体积 + 本次新增占用
    - **历次发布记录对比**：时间线，可回看每次发布了什么

## 5. 接口草案

```
GET    /api/icons/status                 三类图的整体状态（每个学生 × 三种类型）
GET    /api/icons/list?type=&filter=      某类型的列表（带 COS 状态、来源、mtime）
POST   /api/icons/sync-cos                拉 COS 基线（dryRun 可选，先出清单再确认）
POST   /api/icons/gen-schaledb            从 schaledb collection 生成 PNG + JPG
POST   /api/icons/crawl-wikiru            抓 wikiru（mode=new|full）
POST   /api/icons/verify                  全量校验，返回不一致清单
GET    /api/icons/candidates/:id_db        异常学生的候选图列表
POST   /api/icons/assign                  人工指定某张 wikiru 图 → 某学生
POST   /api/icons/upload                  手动上传（type + id_db + 文件）
DELETE /api/icons/:type/:id_db            删除单张
GET    /api/iconview/:type/:id_db         图片预览（本地优先，回退 COS）
```

## 6. 技术选型

- **图像库：`sharp`**（已实测：4ms 读 webp，extract/resize/png/jpeg 全通，约 30MB，跨平台预编译二进制）。
  `jimp` 已排除——默认不支持 webp 解码（`Mime type image/webp does not support decoding`）。
- wikiru 抓来的 `_icon.png` **原样存储**，不重新编码（保真 + 省 CPU）。
- 代理：配置项 `wikiruProxy`（默认空 = 直连）。本机实测直连可达，但别的机器可能需要。

## 7. 验收标准

- [ ] 执行「同步 COS 基线」后，本地 gacha 269 / icon_png 268 / icon_jpg 91，与 COS 一致
- [ ] 执行「从 schaledb 生成」后，270 个学生全部有 icon_png + icon_jpg，尺寸均为 200×226
- [ ] 执行「抓取 wikiru（新增优先）」后，缺失的 gacha 图被补齐；已存在的**不被覆盖**
- [ ] 异常条目能在管理页看到并点选候选图确认
- [ ] 手动上传的图能覆盖自动生成的图，且再次跑自动生成**不会**冲掉手动结果
- [ ] 发布确认页能折叠每个 JSON、显示字段级 diff、显示图片清单与体积
- [ ] 发布后 COS 上三个前缀的图片与本地一致

## 8. 风险

| 风险 | 应对 |
|---|---|
| wikiru 页面结构改版 | 解析失败给明确报错 + 保留「手动上传」兜底 |
| 别的电脑连不上 wikiru | 可配置代理；失败时提示去发布页手动传 |
| 部分角色映射不上（如圣娅） | 走「异常 → 列候选 → 人工点选」流程 |
| 自动生成冲掉人工修正 | 记录每张图的 `source`（auto/manual/cos），manual 优先级最高 |

## 附录 A：图源实测记录

### gacha-img = wikiru 的 `_icon.png`（铁证）
对 27 个样本做 NCC 像素比对（本地 18 张 + COS 抽 9 张）：

- **25 个命中 NCC = 1.000**（像素完全一致），匹配到的文件名就是对应日文名 + `_icon.png`
- 2 个异常：`10098 星野(武装)`、`10110 圣娅` —— 与 wikiru 任何 icon 最高只到 0.34，
  属 **COS 现存数据自身对不上**，需人工确认
- 例：`10136 艾米(武装)` → `エイミ（臨戦）_icon.png`；`16020 御伽` → `オトギ_icon2.png`

### 被证伪的两条路（不要重复走）
1. ❌ 「gacha 图 = schaledb 立绘 `portrait/{Id}.webp` 的脸部裁剪」
   —— 图案确实是同一张立绘（NCC 0.96~0.997），但**真凶不是它**，wikiru 直接有成品图。
2. ❌ 「用 schaledb `collection`/`icon` 做 NCC 与 wikiru icon 互相消歧」
   —— 构图完全不同（半身 vs 大头照），NCC 只有 −0.1~0.16，噪声级，3 行里错 1 行。
   **像素相似度只能做事后异常标记，不能做消歧。**

### COS 存量（2026-09-11 HEAD 探测 270 个 id）
- `gacha-img/`：269 张（缺 10148、20060）
- `stu_icon_db_png/`：268 张
- `stu_icon_db/`（jpg）：91 张
- 本地 `D:\fmps\data\gacha-img`：仅 18 张（不完整副本）
